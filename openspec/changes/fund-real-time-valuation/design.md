## Context

基金净值每日收盘后(约 20:00+)才公布,交易时段内投资者无法感知自选基金实时表现。本项目构建一个参考级精度的基金实时估值服务:基于公开的季报持仓与实时行情,在盘中估算自选基金净值。

经实测验证的数据源(2026-08 验证):

| 数据源 | 用途 | 状态 |
|---|---|---|
| `push2.eastmoney.com/api/qt/stock/get` | 实时行情(股票/指数/可转债),支持批量 `ulist.np` | ✅ 可用,接口宽容 |
| `fundmobapi.eastmoney.com/FundMNewApi/FundBaseTypeInformation.ashx` | 基金基础信息(名称、类型、昨日净值) | ✅ 可用,存在反爬限流(61136403) |
| `fundmobapi.../FundGsz`、`FundStockHold` | 实时估值、持仓明细 | ⚠️ 需要特定 UA/参数,易触发限流 |

关键约束:基金接口有反爬限流,必须把对基金接口的调用压到每日低频;行情接口宽容,盘中高频批量走行情接口。

## Goals / Non-Goals

**Goals:**
- 覆盖 A 股指数型、指数增强、主动股票、混合、债券五类基金的参考级估值
- 多用户自选基金,盘中定时估算并 SSE 推送
- 单只基金详情页展示持仓明细与当日估值历史曲线
- 采用 Java/Spring Boot 3 + MySQL 8 单体服务,单机可部署

**Non-Goals:**
- 高精度估值(与官方净值精确对齐)——后续迭代
- 港股、美股、QDII、货币基金支持——后续迭代
- 全市场基金估值(仅自选驱动计算)
- 基金申赎、交易、账户管理等金融业务功能

## Decisions

### D1: 场景驱动——"自选驱动"的行情采集,而非全市场扫描
盘中只采集用户自选基金所需的行情标的:将全部自选基金的持仓拉平 → 去重(同股多基金共享)→ 批量请求。

**理由**: 自选基金通常几十只,重仓股去重后仅百来只,一次 `ulist.np` 批量请求即可覆盖;大幅降低请求量、避开限流。全市场扫描对参考级工具是浪费。

**备选**: 全市场行情采集(缓存整市)→ 成本高、无必要,否决。

### D2: 模型分派——按基金类型分派估值模型

```
估算净值 = 昨日净值 × (1 + 估算涨跌幅)

类型分派:
- index     : 估算涨跌幅 = 跟踪指数涨跌幅 × 跟踪系数(默认1.0)
- enhanced  : 指数涨跌幅为主体 + 前十大重仓股涨跌幅加权修正
- active    : Σ(重仓股权重 × 涨幅) + 残差项(未披露仓位按0)
- mixed     : 股票段%×股票加权涨跌 + 债券段%×债券段涨跌 + 现金段%×0
- bond      : 重仓可转债实时行情 + 利率债/信用债近似0
```

**理由**: 指数基金成分透明,直接用指数最准最省;混合基金用季报资产配置比例分段,是免费且显著提升精度的数据;债券基金在银行间市场无实时行情,可转债是唯一可实时跟踪的部分,参考级够用。

**备选**: 全部基金统一用重仓股模型 → 指数基金误差反而更大,否决。

### D3: 存储层——MySQL 5 张核心表 + 行情缓存
```
fund              基金主数据: code PK, name, type, track_index, prev_nav, nav_date, fresh_flag
fund_holding      持仓: fund_code+report_qt 维度, stock_code, weight
fund_asset_alloc  资产配置: fund_code+report_qt, stock_pct, bond_pct, cash_pct
estimate_history  估值历史: id, fund_code, est_time, est_nav, est_pct
user_fund         自选: user_id + fund_code, sort_no
quote_cache       行情缓存(盘中覆盖写,不积累)
```
估值结果不入库,盘中实时计算后直接响应/推送,仅历史估值落 `estimate_history`。

**理由**: 参考级规模(几十用户 × 几十基金)下 MySQL 完全胜任;SQLite 在多用户场景下并发写较弱,PostgreSQL 相对重,MySQL 是团队明确选择。

**注(实现期决策)**: 持久层最终采用 **MyBatis-Plus**(`mybatis-plus-spring-boot3-starter`)替代 Spring Data JPA——团队更熟悉 MyBatis 生态,且可规避 Hibernate 持久化上下文对"删除+重建持仓"场景的 flush 干扰。实体使用 `@TableName/@TableId`,查询使用 `LambdaQueryWrapper`,表结构不变。

### D4: 行情代码体系统一——secid 映射
统一使用东财 secid 格式:
```
沪市股票 SH600519 → 1.600519   深市股票 SZ000001 → 0.000001
沪市指数 SH000001 → 1.000001   深市指数 SZ399001 → 0.399001
沪市可转债 SH113050 → 1.113050 深市可转债 SZ123775 → 0.123775
```
持仓代码(带 SH/SZ 前缀)通过前缀映射为 secid,与行情接口对齐。

### D5: 任务调度——三类定时任务
| 任务 | 频率 | 数据源 | 说明 |
|---|---|---|---|
| 净值更新 | 每日 20:30 | fundmobapi(基础信息) | 更新自选基金的昨日净值;限流退避 |
| 持仓更新 | 每日 21:00 | fundmobapi(FundStockHold) | 更新前十大重仓股+资产配置;报告期变更检测 |
| 盘中行情+估值 | 交易时段每 2min | push2 批量 | 拉行情 → 计算估值 → 写历史 → SSE 推送 |

交易时段判定:工作日 9:30-11:30、13:00-15:00(午间休市跳过)。

### D6: 实时推送——SSE 而非 WebSocket
盘中估值更新通过 SSE 单向推送给在线用户;用户建立 SSE 连接时先推送当前快照,后续推增量。

**理由**: 场景是"用户看自选估值列表",单向推送即可;SSE 基于 HTTP,Spring MVC 原生支持,无额外依赖、无连接协议复杂度。WebSocket 双向能力用不上。

**备选**: WebSocket/STOMP → 复杂度高;前端轮询 → 延迟与流量不可控。

### D7: 限流治理
- 基金接口(fundmobapi): 全局串行队列 + 最小间隔(如 500ms)+ 指数退避重试 + UA 轮换;每日低频调用
- 行情接口(push2): 批量请求为主,控制 QPS,失败指数退避
- 所有外部调用统一走带超时、重试、熔断的 HTTP 客户端封装

### D8: 新鲜度标记贯穿输出
每只基金的估值结果均携带:净值日期(nav_date)、持仓报告期(report_qt)、行情时间(quote_ts),并附"估值仅供参考"免责声明。持仓缺失/指数缺失等降级情况显式标记。

## Risks / Trade-offs

- **[持仓滞后导致估值失真]** 季报前十大重仓披露滞后最长 3 个月,基金经理可能已调仓 → 明示持仓报告期,定位为参考级;后续可引入"重仓股近期成交额变化"等弱信号修正(迭代项)。
- **[基金接口反爬限流]** fundmobapi 实测限流(61136403) → 低频采集 + 限流退避 + UA 轮换;行情全部走宽容的 push2。
- **[债券基金估值参考意义有限]** 利率债/信用债无实时行情 → 明确标注债券段为近似,不承诺精度。
- **[跟踪指数缺失]** 部分指数基金无法确定跟踪指数 → 降级为重仓股模型并标记原因。
- **[数据源接口变动]** 东财/天天基金接口为非官方、可能变更 → HTTP 客户端统一封装,接口解析集中,便于接口变更时单点修复。
- **[历史表增长]** 盘中每 2min 落一条,自选较多时增长快 → 保留 30 天 + 定期清理任务。

## Migration Plan

全新项目,无既有数据迁移。部署步骤:
1. 初始化 MySQL 库表(提供建表 SQL 脚本)
2. 打包 Spring Boot 单体应用,单机部署
3. 配置数据源与调度参数(application.yml)
4. 首批自选基金由用户手动添加,系统自动完成元数据/持仓采集
